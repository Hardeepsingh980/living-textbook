## 2026-10-16 (night): stories come alive

Hardeep's ask: interactive storytelling for fiction too, a different engine that generates video if needed, a review by a model that can watch video, take its feedback and go again, and five examples.

**The engine** (`apps/server/src/story`, README there). Gemini 4 Argon reads the pages and plans the film: the book's own sentences and dialogue in the book's order, the cast with a voice and an acting style each, 5 to 8 shots, one choice, characters to talk to, a quiz and a music brief. A page that holds the story but no shot is planned again; a page that is an exercise can be marked "not the story". Nano Banana draws a cast sheet and every opening frame in the book's style; a shot whose moment is printed starts from the printed picture, extended to 16:9. Gemini Omni Flash (`gemini-omni-1.1-flash-preview`, Vertex, Interactions API) films each shot: 10 s, 720p, about 45 s and $1 a clip. Gemini 3.8 TTS acts every line (the style travels as `speechMetadata.style` and is never read aloud; tags such as `<gasp>` are performed). Lyria writes the music. The film is put together with ffmpeg.

**The review loop.** Gemini 4 Argon watches each version of the film next to the pages and a timeline of every shot and line, scores eleven qualities, lists each shot's problems with times, and gives one fix per shot: edit the clip (Omni's own edit, "keep everything else the same"), film it again from a new plan, act lines again, add a pause, change the mix, or change who is in the shot. What the first reviews taught the engine, all now built in:
- Timecodes in a clip prompt ("[0-3s] ...") make Omni cut and dissolve inside a clip; "first, then, finally" plus the `image_to_video` task keeps one continuous shot.
- Omni sometimes adds voices (Hindi, Bengali, English) despite "no dialogue"; Gemini listens to every clip and a clip with speech plays without its own sound.
- Filming again can make a shot worse (the stag fable went 6, 7, then 5), so every shot keeps its takes with their scores and a clearly worse take is replaced by the best one.
- An edit that did not fix a shot is not tried again; the shot is filmed again, told which mistakes to avoid.
- A character whose look changes (Gopal's disguise) needs the changed look in every later shot, so shots carry per-character looks.
- Nano Banana answers "OTHER" without an image under load; it now waits longer between tries before falling back. Lyria can refuse a brief that sounds like a known piece; it then tries new seeds and a plainer brief.

**The app.** `/story/:id` plays a story: the page with its printed picture marked, the picture growing to fill the screen as it starts to move, captions with the speaker's name, the choice as two post-its (the other option shown as "Imagine...", then back to the book), the end with the moral, a quiz, and a live voice chat with a character in its own voice (the live proxy takes `story:<id>:<character>`). Stories are a tab in the library, a card on the dashboard and in New, "Make it a film" on a scanned story page, and a section on the homepage. `POST /api/stories` runs as a background job, two a day per reader and twenty a day in all.

## 2026-10-14: a developer platform (API keys, REST API, embeds, SDK, docs)

Hardeep's ask: SDK and developer docs, so other learning apps can add Living Textbook as a third-party plugin, with API keys in the dashboard and an embed option.

**Keys.** The dashboard has a Developers page (/app/developers). A *secret* key (`ltsk_`, 40 random base62 characters) is for a partner's server; it is shown once and only its SHA-256 hash is stored (the Firestore document id in `devkeys`). A *publishable* key (`ltpk_`) is for web pages: it lists up to ten sites (an exact `https://` site, `https://*.site` for subdomains, or `http://localhost:<port>`), is public by design and stays visible in the dashboard. Keys can be renamed, have their sites edited, and be revoked (lookups are cached for 30 s, so a revoked key stops everywhere within a minute). Usage per UTC day per key lives in `devusage`.

**REST API (/v1).** `POST /v1/lessons` takes a page as multipart, a raw image, JSON `image_base64`, or `image_url` (fetched over https only; every address the name resolves to must be public, checked at connection time so DNS cannot change between the check and the connection; three redirects, 15 MB, 12 s). It runs the normal pipeline inside the request (Cloud Run keeps the CPU) and answers 201 with the lesson after 10–30 s, or streams `progress` events then `lesson` with `?stream=true`. Then `GET /v1/lessons/{id}`, `GET /v1/lessons` (paged, filter by `external_user_id`), `DELETE`, `GET /v1/lessons/{id}/quiz`, `GET /v1/usage`, and `/v1/openapi.json`. Lessons made with keys belong to `api-<uid>`, apart from the developer's own library; the partner's `external_user_id` and `metadata` come back with the lesson and never appear on public records. Errors are `{ error: { type, code, message } }` with stable codes; limits are 50 lessons a day per account and 6 a minute per key, reported in `X-RateLimit-*` headers.

**Embeds.** `/embed/lesson/<id>` is the lesson view without the app around it (any site may frame it). `/embed/scan?key=ltpk_...` is the scanner (camera or photo), allowed in frames only on the key's sites: the server answers it with `Content-Security-Policy: frame-ancestors 'self' <sites>`, and the frame also sends the site it is on (`ancestorOrigins`, else the referrer, which the SDK sets with `referrerpolicy=origin`) with the lesson request, checked against the key. Every other page may be framed only by this site. Scanner lessons count against the partner's allowance, at most 15 a day per visitor per key. The frames post `ready`, `step`, `complete`, `quiz.completed`, `lesson.created`, `close` and `error` to the host page and take `play`, `pause`, `goTo` and `mute`; a `goTo` that arrives before the lesson has begun becomes its first step. Inside an embed nobody signs in (Firebase does not start).

**SDK (packages/sdk).** One TypeScript source builds three things: `/sdk/v1.js` (5 KB, a script tag: `LivingTextbook().lesson('#el', { lessonId })`, `.scanner({ onLesson })`, and `data-lt-lesson` / `data-lt-scanner` attributes for no-code use), the ESM package with types (`new LivingTextbook({ apiKey }).lessons.create({ image, onProgress })`, retrieve, list, `allLessons()`, del, quiz, usage), and `/sdk/living-textbook-sdk.tgz`, which `npm install <url>` accepts. The SDK refuses a secret key in a web page and a publishable key on a server.

**Docs (/developers).** Overview, quick start, keys, the player, the scanner, events and commands, the REST reference with curl, the lesson object, errors, limits, the Node SDK, plain iframes, security and privacy; examples use the address the docs are served from, so they work as written. Links from the homepage, the app's top bar and the account menu.

**Checked.** Unit tests for keys, sites, address blocking and input limits (server, 12) and for the client and its event-stream reader (SDK, 10). An end-to-end script (`apps/server/scripts/dev-platform-test.mts`, 34 checks) makes keys, makes a lesson with the SDK (30 s, streamed), reads, lists, quizzes and deletes it, checks every error, makes a lesson through the scanner path, checks the frame rules and the SDK files, and revokes its keys. A partner page on another origin loaded the script, showed a lesson (events and `goTo` arrived), opened the scanner, uploaded a page and received `lesson.created`; on a site the key does not list, the browser refused the scanner frame.

## 2026-10-12 (afternoon): the lesson, conducted; text off the motion; depth

Hardeep's asks, from two phone screenshots (heat along a rod, the heart): notes sat on the animation; a speech bubble's arrow was drawn on the bubble itself; the tutor asked "any questions?" before it had finished, so the lesson should be narrated in full (with the reader free to interrupt) and questions invited only at the end; and the lessons looked flat, so better quality and some 3D.

**The lesson is conducted by the app.** The app moves the page to a step and sends the tutor that one step ("LESSON STEP n OF N" with its script); the tutor explains it in three or four sentences and stops; the next step goes out only when a turn in which the tutor actually spoke has finished and its audio has played. Only after the last step does the app send "LESSON END": the tutor shows one what-if with the tools, puts the value back, and only then invites questions. If the reader speaks during a step, the tutor answers and the app then asks it to finish that step. The first version raced: Gemini Live often calls a tool (highlight, scene state) before speaking, and that tool-only turn ends with its own turn-complete, which the app took as the end of the step, so each step was cut off by the next. Turns now report whether they spoke, and a watchdog re-sends a step that never starts (then moves on). Traced on six pages (step, tutor state, caption every 0.4 s): every step narrated in full and in order, steps 0.4–1 s apart, no questions before the end, lessons 50–85 s.

**Text off the motion.** The layout now sweeps every moving element over time (25 samples with all elements shown) and keeps labels, readouts and bubbles out of those footprints, out of a bubble's speaker (the point its tail aims at, and the whole drawing when the speaker is printed) and out of the caption strip (now the bottom 13 %). When no blank spot exists, a note no longer stays where it was; it takes the least-inked spot that covers none of those. Bubble sizes match what the renderer draws (the old thought ellipse was 40 % wider than the space reserved for it and covered Paheli).

**Bubbles.** Thought bubbles are clouds of puffs hugging the text, with three trailing circles towards the speaker; speech tails leave from the edge that faces the speaker, drawn under the body, so no arrow ever sits on the bubble.

**Depth.** Notes, bubbles and characters stand up from the page like a pop-up book (on their bottom edge, a touch past upright, then settling) and cast soft blurred shadows on the paper; solid shapes get a highlight and shade; flow beads have a glint. In AR the tracker's pose gives the parallax of a point raised above the page (projected through the camera and mapped back onto the page plane), so floating notes shift against the paper as the phone moves. Transparent and outline shapes stay flat (the first version put a white glare and a dark shadow on the heart's transparent pulse ring).

**Quality.** A readout whose value never changes was measured before the hand-drawn font loaded and stayed clipped; notes are now measured after the font loads and again whenever a font arrives. The scene prompt adds: short readouts; bubbles beside their speaker; nothing in the bottom eighth; and a body diagram's left and right follow its printed callouts (the heart's labels had been swapped). Verification: narration and labels the verifier rewrote settle the checks they fixed (the heart showed a red cross although its narration had been corrected); corrected formulas apply without a worked example; any figure printed on the page is on topic (the resistor page prints a parallel circuit above the series section); and a correct fact the page does not state is shown as a note ("Beyond this page") instead of a failure. Six regenerated pages: all verified.

**Phones.** The caption and controls fit a 360 px screen; Save moves beside Quiz so the title fits the top bar.

**Every window (Hardeep's desktop screenshot: the photo filled the window and was cropped).** The page photo was scaled to cover the screen, which cropped it top and bottom on a desktop and cut its margins off on a phone, hiding notes placed there. It is now fitted whole into the room the bars leave for it. On desktops and landscape tablets the page and a docked lesson panel (caption, what-if slider, controls, steps, how it was made) are one group centred in the window, with the top bar spanning the group; on phones and portrait tablets the page sits above the caption and controls, and captions keep their latest three lines. Checked at 1462×928, 1280×720, 1180×820, 820×1180 and 390×844: the whole page inside the window and nothing over it. Recording mode is unchanged.

Cloud Run only gives a container CPU while a request is open, so each job runs inside a request of its own: the API enqueues a Cloud Task (queue `living-book-jobs`, asia-south1, four at a time, two attempts, 30-minute deadline; the service timeout is now 1800 s) that calls `POST /api/jobs/:id/run`, which claims the job in a transaction and runs it; one heavy job per instance at a time. Verified on the live service: a short video ran end to end with no client attached (ready in 56 s), and locally a chapter film kept going while its page was closed for 90 s.

**Also.** Video files are served with byte ranges (iPhones will not play an MP4 without them, and seeking needs them everywhere). Local development can sign in a test reader (server `DEV_USERS=1`, `localStorage.lb.devUser`), never enabled on Cloud Run.

**AR tracking (spike, `spikes/tracking`):** WebXR is unavailable on iOS Safari and Chrome image tracking is flag-only, so tracking uses MindAR's tracker and matcher directly:
- *Capture-seeded tracking*: the captured frame is the target; its tracking templates are extracted on-device in ~0.2–0.6 s of pure JS (worker) and the tracker starts from the known capture pose. Nothing waits for the server.
- *Server detection data* (for re-acquisition after loss) compiles in 2.1 s at 640 px / 3.0 s at 800 px across worker threads; re-acquisition then takes 20–100 ms.
- *Pre-warm*: WebGL kernel compilation costs ~6 s cold on desktop Chrome and is done while the user frames the page (0.2 s when warm).
- *Template resolution*: MindAR's default 128 px keyframe gave 3–15 templates on a text page; 256 px gave 15–50 and stable tracking in simulation; the `kf` parameter lets us compare on phones.
- *Photo mode* fallback (experience warped onto the frozen capture) is in place and aligned by construction.
- Real-device numbers (Android phone, iPad) are still pending Hardeep's test of the spike URL.
